# CareerMate P1 — Core Loop Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A candidate applies to a real job and watches it move through stages; the employer who posted it sees that application arrive and moves it forward.

**Architecture:** Unchanged from P0 — components take props, pages guard and call a service, services decide authorization, repositories own Prisma. P1 adds the write side: every mutation is a server action that re-checks authorization in its service, because a server action is a public endpoint addressed by a build-hash id and does not run the route-group layout that guards its page.

**Tech Stack:** As P0. No new runtime dependencies.

**Spec:** [`docs/superpowers/specs/2026-09-23-careermate-rebuild-design.md`](../specs/2026-09-23-careermate-rebuild-design.md) §3, §4, §7

## Global Constraints

- **Every server action's service re-checks role and ownership.** The layout guard protects the page, not the action. This is how P0's two Critical findings happened; it does not happen twice.
- **Every stage change writes an `ApplicationEvent`.** The tracker renders history, so a stage that moves without an event is data loss. The service writes both in one transaction.
- **Ownership for an employer means `job.companyId === their EmployerProfile.companyId`**, never `postedById`. A colleague at the same company must be able to review applications to a role someone else posted.
- Double-applying is prevented by the database's `@@unique([candidateProfileId, jobId])`, not by a read-then-write check. Services catch Prisma `P2002` and return `CONFLICT`.
- A candidate may only ever read their own applications; an employer only applications to their own company's jobs; an admin either. No query trusts an id from the URL without an ownership predicate **in the `where` clause** — not as a check after fetching.
- Draft and closed jobs are never reachable from a candidate route. `findPublishedJob` already applies that pair; new candidate-facing reads use it or repeat it.
- New Prisma migrations are committed, and any new table gets the same deny-all treatment as `20260923000001_rls_deny_all` (`tests/unit/rls-migration.test.ts` enforces this).

## Review Focus

Five conditions the spec implies that no feature task naturally exercises.

1. **Two concurrent submissions of the same application** (double-clicked submit, or a replayed request). Expected: one row, the second returns CONFLICT and the UI shows "you have already applied" — not a 500 from the unique constraint. → Task 4.
2. **An employer changing the stage of an application belonging to another company's job**, by posting that application's id to the stage action. Expected: FORBIDDEN, nothing written, no event. → Task 8.
3. **A candidate applying to a job that was closed between page load and submit.** Expected: rejected with "this role is no longer accepting applications", no orphan row. → Task 4.
4. **An employer publishing a job with a salary range whose minimum exceeds its maximum**, or with an empty responsibilities list. Expected: field errors, nothing written. → Task 6.
5. **A candidate opening `/tracker` or `/apply/[id]` with another candidate's application or a nonexistent job id.** Expected: 404, never another person's data and never a distinguishable "exists but forbidden". → Tasks 4, 5.
